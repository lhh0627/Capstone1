# Capstone1

Executive SummarySecurity Operations Centres (SOCs) receive more alerts than analysts can investigate carefully. The first look at each alert, known as Tier-1 triage, is repetitive, slow and easy to get wrong when workloads are high. This project builds an AI-assisted Tier-1 triage assistant for Wazuh, an open-source security monitoring platform.   When Wazuh raises an alert, the system collects the related logs, extracts indicators such as IP addresses and file hashes, and checks them against threat-intelligence services and a host inventory. A large language model (LLM), accessed through a hosted API, then reads this evidence and writes a structured triage report containing a verdict, the matching MITRE ATT&CK technique, the supporting evidence and a recommended action. A validator rejects any report that breaks the required format or cites evidence that does not exist. A web console shows the report to a human analyst, who approves or rejects the action. The system never acts on its own, and containment is simulated and logged.   The team will build and test the system in an isolated lab with two attack scenarios, SSH credential attacks on Linux and PowerShell living-off-the-land activity on Windows. It will be evaluated on about 80 labelled alerts against three baselines. This document sets out the problem, the objectives, the functionality, the scope, the 16-week plan and the team organisation.   Project Purpose1. Problem StatementSOC analysts must validate the alerts raised by monitoring tools such as SIEM platforms. In a qualitative study with 21 practitioners from seven SOCs, Alahmadi et al. (2022) found that most alarms analysts regarded as false positives were benign triggers, meaning real detections that are explained by legitimate activity in the organisation. They also found that alarm validation is a tedious, human-centred task that can lead to alarm burnout and desensitisation. When analysts become desensitised, genuine attacks risk being treated as noise.   Slow detection and response is costly. IBM’s 2025 study reported a global mean time to identify and contain a breach of 241 days and an average breach cost of US$4.44 million (Kapko, 2025). Shortening the time between an alert and a correct decision is a practical way to reduce the damage of an intrusion, and Tier-1 triage is the first step at which time is lost.   LLMs are an active area of cybersecurity research: a systematic review analysed 127 papers on their use in security tasks (Xu et al., 2024). LLMs can read varied log text and write explanations, which suits triage. However, their output can be unreliable, and attacker-controlled text inside logs can try to manipulate them. A triage assistant therefore needs evidence checking, restricted read-only tools and human approval before any action. What is still needed is evidence of how well such a design performs on Wazuh alerts, compared with a human analyst and with simple baselines.   Problem statement: how can an LLM agent perform Tier-1 triage of Wazuh alerts accurately, quickly and with verifiable evidence, while keeping a human analyst in control of every action? The proposed computing-based approach combines automated log collection, threat-intelligence enrichment, an LLM agent with a fixed set of read-only tools, a report validator and a human-in-the-loop console, and measures the result on labelled lab alerts.   Project ObjectivesDesign and develop an automated pipeline that ingests Wazuh alerts, collects the related logs and enriches indicators with threat intelligence, producing a triage report for each alert in a median time of under 60 seconds.   Implement an LLM-based triage agent, with structured JSON output and read-only tools, that assigns a verdict (true positive, false positive or escalate) and a MITRE ATT&CK technique to each alert, targeting at least 80% accuracy and 90% recall on malicious alerts in a 60-alert test set.   Develop validation guardrails (JSON schema check, evidence-citation check and prompt-injection handling) so that at most 5% of the claims in a report lack supporting evidence.   Develop a human-in-the-loop web console in which an analyst reviews the evidence and approves or rejects the recommended action, with every decision stored in an audit log.   Evaluate the system against three baselines (Wazuh rule level, the same LLM without enrichment, and a human analyst) on about 80 labelled alerts from two attack scenarios, reporting accuracy, groundedness, consistency, time and cost. Project Description, Scope and Management MilestonesProject DescriptionApproach: The project follows an iterative build-and-measure approach. The team first builds an isolated lab with Wazuh and victim machines and generates alerts from two scenarios: SSH credential attacks (MITRE ATT&CK T1110 Brute Force and T1078 Valid Accounts) and PowerShell living-off-the-land activity (T1059.001, T1105 and T1027) (MITRE, n.d.). Two team members label each alert independently to create a ground-truth dataset of about 80 alerts, half malicious and half benign look-alikes. Twenty alerts are used to develop prompts and 60 are locked as a test set.   Solution: The solution is a Python backend with five stages:   Alert ingestion and log collection;   Indicator extraction and cached enrichment from AbuseIPDB, VirusTotal and a host inventory file;   A triage agent that calls a hosted LLM through a tool-calling API, with structured JSON output, a fixed set of read-only tools and a six-step limit;   A validator that checks the JSON schema and that every claim cites an evidence ID; and   A web console where an analyst approves or rejects the recommended action, with every decision stored in an audit log. A replay mode runs the pipeline on stored alerts so that results are repeatable.   Customers and benefits: The intended users are Tier-1 SOC analysts and small security teams that lack the staff to review every alert. The expected benefits are faster first-look triage, consistent and evidence-cited reports, and analysts who spend their time on decisions instead of data gathering. The project also produces a labelled alert dataset and a measured evaluation that others can reuse.   ScopeWho: A team of five students (three AI, two cybersecurity) under a project supervisor. The intended users are SOC analysts; fellow students act as analysts in the analyst-time study.   What is in scope: Two attack scenarios (SSH credential attack, PowerShell living-off-the-land); a Wazuh lab with Linux and Windows victim machines; threat-intelligence enrichment from two APIs; a hosted LLM triage agent with a report validator; an analyst console with an audit log and simulated containment; a template incident summary; and an evaluation with baselines.   What is out of scope: Ransomware, lateral-movement and data-exfiltration scenarios; Active Directory integration (replaced by a host CSV file); real containment actions on any host; legal mapping of incidents to regulations such as PDPA or GDPR; production deployment; and training or fine-tuning an LLM.   Where: The lab runs on the team’s own computers on an isolated host-only network. The LLM is reached through a hosted API, and the console runs locally.   When: 16 weeks, with three gates:   Gate 1 (end of week 7): One scenario works end to end and 40 alerts are labelled.   Gate 2 (end of week 11): Feature freeze.   Gate 3 (end of week 14): Results frozen.   Why: To measure, on realistic alerts, whether an LLM agent can reduce Tier-1 triage effort without losing correctness or human control.   If the schedule slips: One scenario, the pipeline, the report and an evaluation on 40 alerts remain a complete project.
